## Production Destination

Files inside `raw/` are temporary working files.

Production code must always be placed into the appropriate project folders.

HTML pages

```
raw/*.html

↓

templates/*.php
```

Styles

```
src/scss/components/

src/scss/pages/
```

JavaScript

```
src/js/
```

After integration, the `raw/` version should only remain as the original reference and must not be considered part of the production application.

# Importing HTML from Claude Design

Source files inside

raw/

are considered temporary.

Never keep generated HTML as-is.

Your goal is to transform generated markup into production-quality code.

Priority order

1. Preserve appearance.
2. Match project architecture.
3. Reuse existing code.
4. Remove duplication.
5. Improve semantics.
6. Improve accessibility.
7. Improve maintainability.

Generated code is only a draft.

Feel free to

- rename classes
- restructure markup
- simplify DOM
- merge duplicated blocks
- extract components
- move CSS
- move JavaScript

Default to preserving the original DOM structure during the first migration.

Restructure or remove wrappers only when you have verified that the change does
not affect:

- CSS selectors;
- animation targets;
- stacking contexts;
- containing blocks;
- overflow clipping;
- flex/grid behavior;
- responsive behavior;
- accessibility relationships.

Prefer a conservative migration over an aggressive cleanup.

The final code should look like it was written manually for this project, not generated by AI.

## PHP Template Rules

At this stage, the goal is only to migrate the HTML into a PHP template.

Do NOT perform any PHP templating or page decomposition.

Do NOT:

- add PHP business logic
- add PHP variables
- add PHP conditions
- add PHP loops
- add PHP functions
- add include()
- add require()
- add require_once()
- extract partials into `includes/`
- create layouts
- create template inheritance
- create reusable PHP components

The resulting file should be a plain PHP template containing only HTML markup.

The `.php` extension is used only because this project renders pages through PHP.

The content should be equivalent to the original HTML body after the CSS and JavaScript have been extracted.

Future refactoring into reusable PHP partials will be performed in a separate task.

# Visual Integrity Rules

The source HTML located in `raw/` represents the approved design.

Your primary responsibility is to preserve the visual result.

The page after refactoring must look **identical** to the original.

Requirements

- Do not change spacing.
- Do not change margins.
- Do not change paddings.
- Do not change typography.
- Do not change colors.
- Do not change animations.
- Do not change transitions.
- Do not change responsive behavior.
- Do not change DOM order unless absolutely necessary.
- Do not change element sizes.
- Do not change visual hierarchy.
- Do not change z-index behavior.
- Do not introduce layout shifts.

Allowed changes

- Move inline CSS into SCSS.
- Move inline JavaScript into JS files.
- Rename classes if required by the project architecture.
- Improve semantic HTML.
- Remove duplicated code.
- Split SCSS into component/page files.
- Split JavaScript into modules.

If a structural change could affect rendering,
choose the safer solution.

When in doubt:

Visual consistency has higher priority than code elegance.

Success criteria

A user comparing the original page from `raw/`
with the integrated page should not notice any visual difference.

The refactoring must be architecture-only,
not design-changing.

During this task, do not extract PHP includes or reusable PHP components.

You may identify and report reusable block candidates, but do not implement
their PHP decomposition.

PHP decomposition belongs to a separate task.
